# ADR-0004: Optional email accounts with the map stored in PostgreSQL

**Status:** superseded by ADR-0005

## Context

A visitor's map, place/food marks, saved trips, profile details, language and map colours
live only in browser localStorage (`ghuri:v1`, `src/lib/store.ts`). "Sign in"
(`src/components/Overlays.tsx`) just stores a name and optional email in that same
localStorage entry; there is no server-side account, no session and no password. Clearing
the browser or opening the site on another device starts from an empty map.

Constraints from the project owner:

- No password for visitors; an email must be optional (the site stays usable without one,
  and an email can be added later to keep the profile).
- The server cannot send email yet (no SMTP), so an emailed link or code cannot be used to
  prove ownership of an address.
- Sync: map (visited / want / favorite districts), place and food marks plus saved trips,
  and profile settings (name, bio, home district, map colours, language).

Typing someone's email address is not proof the address is theirs. Without email
delivery, "log in with just an email" would let anyone open or overwrite another person's
map by typing their email.

## Decision

Introduce optional server-side accounts, stored in the existing PostgreSQL database.

- **Anonymous first.** The first time a visitor chooses "Save my map online", the server
  creates an account (random id) and sets an HTTP-only session cookie. No email needed.
- **Email is optional.** A visitor can attach an email to the account. It is stored
  lowercased and unique, and shown as a label only until email delivery exists.
- **Signing in on another device** needs the email **and** a **recovery code**: a long
  random code generated by the server when the account is created, shown once and
  stored only as a hash. This avoids passwords the visitor has to invent, and keeps
  email-only impersonation impossible. When SMTP is added later, an emailed sign-in code
  replaces the recovery code (a new ADR will record that change).
- **Data model** (Prisma, migration added): `Account` (id, optional unique email,
  recovery-code hash, created-at), `Session` (id, account, token hash, expires-at),
  `AccountState` (account, JSON snapshot of `districtMarks`, `placeMarks`, `foodMarks`,
  `trips`, and profile settings, plus updated-at).
- **Sync rule:** the browser keeps working offline from localStorage. When signed in, it
  loads the server snapshot on start and saves changes (debounced). Conflicts use
  last-write-wins on the whole snapshot; the first sign-in on a device with local data
  asks whether to keep the server copy or the local copy.
- **API:** `POST /api/account` (create), `POST /api/account/login`, `POST
  /api/account/logout`, `PUT /api/account/email`, `GET|PUT /api/account/state`, all
  validated with the same sanitising approach as `profileStore.ts`, rate-limited, and
  authorising only from the session cookie (never from a client-supplied account id).
- **No new dependencies:** codes and tokens use Node's built-in `crypto` (scrypt for the
  recovery code, SHA-256 for session tokens).

## Consequences

- A visitor's map follows them across devices, and survives clearing the browser.
- Losing the recovery code means losing access from a new device (the current device stays
  signed in until the cookie expires). There is no email reset until SMTP exists.
- Adds server-side personal data (optional email, map data), so the privacy note in the
  share dialog and a short privacy statement need updating, and a "delete my account"
  action is required.
- Changes the data model (three tables) and adds authentication, which this ADR covers.
- The public profile (ADR-0003) is unchanged and remains a separate, opt-in snapshot.
